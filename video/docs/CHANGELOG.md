# История изменений CorpVideo

## 1.13.0 — раздел «Видео» портала документации (10 октября 2026)

CorpVideo встроен в портал документации 1.8.0 как раздел «Видео» по адресу `/video`: один сайт, один
вход, общие роли. Отдельной установки больше нет — видеопортал ставят, обновляют, копируют и удаляют
скрипты портала (`docportal video enable`, см. руководство портала).

### Работа под префиксом пути

- `BASE_PATH` (например, `/video`): nginx срезает префикс перед API, маршруты не меняются; всё, что
  видит браузер (медиафайлы, ссылки на API, перенаправления, манифест, service worker, WebSocket,
  ссылки «Поделиться», QR-коды, код встраивания, ICS), несёт префикс. Веб-интерфейс собирается с
  `VITE_BASE=/video/`. Внутренние адреса nginx — `/__corpvideo_media_auth`, `/__corpvideo_internal_media/`.
- Исправлено: письмо о записи на вебинар (ссылка на материалы), ссылка канала в RSS (`/@handle`).

### Общий вход с порталом документации

- Режим портала (`PORTAL_INTERNAL_URL` + `PORTAL_SHARED_SECRET`): видеопортал не хранит паролей и не
  показывает свою форму входа — на запрос браузера он спрашивает портал (`/internal/video/session`,
  внутренний адрес, запрос подписан общим секретом), кто вошёл; учитываются второй фактор, блокировка,
  обязательная смена пароля. Ответ кэшируется на 10 секунд; новые cookie «Запомнить меня» передаются
  браузеру. Выход — общий.
- Учётные записи заводятся и обновляются по данным портала (`portal_user_id`; прежняя учётная запись
  с той же почтой привязывается со всеми каналами и видео). Роли: администратор → администратор;
  маркетолог и модератор раздела → модератор (загрузка и эфиры); помощник маркетолога → загрузка с
  премодерацией; пользователь → просмотр.
- В режиме портала выключены и скрыты регистрация, вход через LDAP и SSO, второй фактор, смена
  пароля; премодерация загрузок включена принудительно. В меню — ссылки на портал и его страницу
  модерации.
- Письма на адреса-заглушки (`…@portal.invalid` — у сотрудников без почты) не отправляются.

### Связь с порталом: сотрудники, уведомления, сведения

- **Справочник сотрудников**: раз в `PORTAL_SYNC_MINUTES` минут (15) и командой `portal-sync`
  видеопортал забирает у портала список сотрудников — заводит учётные записи всем активным (обязательный
  просмотр можно назначить и тому, кто ещё не заходил), блокирует заблокированных и удалённых в портале
  (`portal_blocked`; вернувшихся разблокирует, блокировку модератором видео не трогает), ведёт группы
  по подразделениям портала (`groups.portal_department`, участники `via_portal`; добавленные вручную
  остаются). Пустой ответ портала при заведённых сотрудниках не применяется. Итог — в `portal_sync_state`.
- **Уведомления о задачах** (модерация, решение модератора, обязательный просмотр и напоминание, жалоба,
  удержанный комментарий, просьба о рецензии, соведущий вебинара, сертификат, ошибка обработки) уходят
  письмом и в Telegram через портал — заданием воркера `portal_notify` (по 50 адресатов); собственные
  письмо и бот видеопортала для них не используются. `PORTAL_NOTIFY=0` — выключить.
- **Сведения для портала** по адресам `/api/internal/status | moderation | search | portal-sync` (только
  с общим секретом; nginx снаружи отвечает 404): состояние (база, обработчик, очередь, место, синхронизация)
  для «Мониторинга», число видео на модерации для шапки, поиск видео для страницы поиска портала.
- Тесты на базе данных: `TEST_DATABASE_URL=… npm run test:portal`.

### Развёртывание

- Образ Docker (`deploy/docker/Dockerfile`) — один, для API и обработки; использует готовые
  `server/node_modules` и `web/dist` из дистрибутива портала (сборка без npm), каталоги данных
  передаёт пользователю `node` при первом запуске (тома Docker создаются пустыми). Скрипт автопоиска
  лиц `scripts/facedetect.py` теперь входит в образ.
- Удалены отдельные установщик, обновление, резервное копирование и Compose-файл — их заменили
  скрипты портала.
- Модульные тесты общего входа: `npm run test:unit` (без базы данных).

## 1.12.1 — обновление нативной установки проходит шаг nginx (7 октября 2026)

Исправление для тех, у кого обновление до 1.12.0 остановилось на шаге nginx с сообщением
«Ошибка конфигурации nginx (nginx -t)», а откат предупредил «Прежняя конфигурация nginx не проходит
проверку».

### Что случилось

- С версии 1.11.0 установщик записывал в `/etc/nginx/conf.d/corpvideo-http.conf` настройки сжатия,
  в том числе `gzip on`. В `nginx.conf` Ubuntu и Debian эта директива уже есть, а повтор в том же
  контексте — ошибка: `"gzip" directive is duplicate`. Поэтому на стандартном nginx не проходили ни
  установка 1.11.0–1.12.0 с нуля, ни обновление на них.
- Откат 1.12.0 возвращал файлы, которые были до обновления, но не удалял тот, которого раньше не
  было, — `corpvideo-http.conf` оставался, и прежняя конфигурация тоже переставала проходить проверку.
  Портал при этом продолжал работать: nginx держит в памяти последнюю удачную конфигурацию. Но
  перезапуск nginx или сервера, а также перезагрузка после продления сертификата на такой
  конфигурации не прошли бы.
- Тесты API и браузерные проверки этого не видели: в песочнице nginx запускался со своим
  `nginx.conf`, а не с дистрибутивным.

### Что исправлено

- Сжатие и `server_tokens off` задаются внутри сайта (в контексте `server`), а не на уровне http, —
  с дистрибутивным `nginx.conf` они больше не конфликтуют и не меняют настройки других сайтов на
  этом сервере. Файл `corpvideo-http.conf` установщик и обновление удаляют.
- `update.sh` в самом начале проверяет текущую конфигурацию nginx и убирает устаревший
  `corpvideo-http.conf`; если конфигурация не проходит проверку и без него — останавливается до
  каких-либо изменений и показывает причину.
- Конфигурация nginx новой версии проверяется **до переключения**: если `nginx -t` не проходит,
  работающая версия, база и службы не трогаются вовсе (в 1.12.0 это выяснялось после переключения
  и миграций).
- Откат удаляет файлы, которых до обновления не было, и возвращает и `corpvideo.env`.
- Ошибка `nginx -t` показывается прямо на экране, а не только в журнале установки.
- Режим Let's Encrypt при уже выданном сертификате больше не проходит через промежуточную
  HTTP-конфигурацию: раньше на время между двумя перезагрузками nginx портал оставался без HTTPS.
- Новый `scripts/dev/test-nginx-native.sh` прогоняет настройку nginx установщиком во всех режимах SSL
  на настоящем nginx с дистрибутивным `nginx.conf` — на 1.12.0 он падает ровно с этой ошибкой.

### Если обновление до 1.12.0 уже остановилось

Портал работает на прежней версии, но конфигурацию nginx на диске нужно вернуть в рабочее
состояние сразу, не дожидаясь обновления:

```bash
sudo rm /etc/nginx/conf.d/corpvideo-http.conf
sudo nginx -t && sudo systemctl reload nginx
```

Затем обычное обновление до 1.12.1 (`sudo ./update.sh` из распакованного архива или после
`git pull`). Миграции базы 013–014 после неудачной попытки уже применены — для прежней версии это
безопасно, они только добавляют. Неудачная сборка `/opt/corpvideo.failed` удалится при следующем
обновлении сама.

## 1.12.0 — надёжность, безопасность и скорость (30 сентября 2026)

Выпуск закрывает разделы 1–5 списка «Что доделать» из 1.11.0: очередь и рассылки, производительность,
безопасность, интерфейс, установку. Обновление обычное: `sudo ./update.sh` (или `corpvideo update`).
Миграция `014_hardening.sql` применяется автоматически и только добавляет — прежняя версия работает
и с обновлённой схемой.

### Самое заметное

- **Вход в час пик.** За nginx все посетители получали один и тот же адрес — адрес самого nginx:
  в используемой версии Fastify числовое значение `TRUST_PROXY` (по умолчанию `1`) перестало
  приниматься и молча означало «не доверять никому». Предел «10 входов в минуту с одного адреса»
  действовал **на весь портал сразу**: утром, когда сотрудники входят одновременно, часть получала
  «Слишком много запросов». Так же делились пределы чата эфира, комментариев и записи на вебинары,
  а в журнале действий и списке сеансов вместо адреса сотрудника стоял адрес nginx. Теперь адрес
  клиента берётся из заголовка, который выставил nginx, и пределы считаются по сотруднику (если он
  вошёл) или по адресу.
- **Обновление с откатом.** Нативная установка собирает новую версию рядом (`/opt/corpvideo.next`),
  работающий портал в это время продолжает отдавать прежний интерфейс. Если миграции, запуск или
  nginx не прошли — каталоги, конфигурация nginx и служб возвращаются сами, портал поднимается на
  прежней версии, а неудачная сборка остаётся в `/opt/corpvideo.failed` для разбора. Прежняя версия
  после успешного обновления хранится в `/opt/corpvideo.prev`. В Docker перед обновлением делается
  снимок файлов, образы прежней версии сохраняются (остальные старые образы удаляются — раньше они
  копились десятками гигабайт).
- **Кнопки «Проверить» в настройках больше не сохраняют форму.** Раньше «Сохранить и проверить»
  сначала записывала значения, и неудачная проверка необратимо меняла рабочую конфигурацию (почта,
  LDAP, SSO, ASR, ИИ, Telegram, база знаний, LRS). Теперь проверяются значения из формы, а
  применяются они только кнопкой «Сохранить».
- **robots.txt через nginx отвечал 404** (с 1.6): его отдавал блок статики, в которой файла нет.
  Поисковики не видели ни карты сайта, ни запрета индексации закрытого портала. Теперь его формирует API.
- **Страница видео на телефоне** была шире экрана: правая часть (кнопки «Настроить канал»,
  «Сохранить», согласование) обрезалась. Исправлено, как и кнопки с длинными подписями в настройках.

### Изменения поведения, о которых стоит знать

- **Вебхуки на сам сервер** (`127.0.0.1`, `localhost`) по умолчанию запрещены: такой адрес открывал
  чтение внутренних служб через панель. Если у вас вебхук действительно смотрит на этот же сервер,
  добавьте `OUTBOUND_ALLOW_LOCAL=1` в конфигурацию и перезапустите портал. Интеграции (ИИ, ASR, база
  знаний, LRS, SSO) на этом же сервере работают как раньше. Служебные адреса `169.254.x.x`
  (метаданные облака) запрещены всегда.
- **Личный токен лент** (`?ft=` в адресах RSS и подкастов) открывает только ленты и вложенные в них
  файлы — обложки, `video.mp4`, `audio.m4a`. Скачать оригинал по нему больше нельзя (только из
  сеанса). У токена появился срок жизни — `feeds.token_days`, по умолчанию 365 дней; для выданных
  раньше токенов срок отсчитывается с момента обновления. Дата видна сотруднику в «Настройки →
  Токены API».
- **Блокировка входа** считается по паре «логин + адрес»: зная почту коллеги, больше нельзя держать
  его учётную запись закрытой. Вся учётная запись блокируется только при втрое большем числе неудач
  с разных адресов. Новый пароль (сброс или `corpvideo cli set-password`) снимает блокировки.
- **Регистрация на занятый адрес** при включённом подтверждении почты выглядит как обычная
  регистрация, а владельцу адреса уходит письмо «у вас уже есть учётная запись» — форма больше не
  подсказывает, кто зарегистрирован на портале.
- **Правка комментария** проходит ту же проверку, что и новый: с запрещёнными словами (или при
  премодерации) изменённый комментарий уходит на проверку автору видео.
- **Docker: папка автоимпорта** — только `/data/import` (на сервере `$DATA_DIR/import`): каталог
  данных целиком в контейнеры больше не монтируется. Обновление предупредит, если в настройках
  указан другой путь.
- **Отключение второго фактора** у доменных учётных записей (LDAP, SSO) требует код из приложения —
  раньше пароль у них считался проверенным всегда.
- **Сводка качества воспроизведения** — только модераторам и администраторам: в ней видны самые
  проблемные видео портала, включая закрытые.

### Очередь заданий, рассылки, эфиры

- **Третья полоса очереди** для многочасовых заданий эфира — ретрансляции и живых субтитров
  (`WORKER_LONG_CONCURRENCY`, по умолчанию 8). Два эфира с ретрансляцией больше не занимают места
  ИИ-заданий на полсуток: конспекты, теги и переводы идут своим чередом.
- **Повторы заданий без привязки к видео** отсекаются по ключу: переподключение источника эфира
  больше не запускает второй ffmpeg на ту же площадку ретрансляции и вторые живые субтитры.
- **Объявление на весь портал** рассылается фоновым заданием пачками по 500 человек — по три запроса
  к базе на пачку, а не на человека. На больших порталах запрос из панели обрывался по таймауту
  nginx, успев разослать часть уведомлений.
- **Завершение и удаление эфира из панели** идут тем же путём, что кнопка в студии: событие и
  вебхук `live.ended`, остановка ретрансляций, импорт записи. Импорт записи эфира ставится
  отложенным заданием воркера (раньше — таймер в процессе API, терявшийся при его перезапуске).
- **Отмена задания** в панели: отменённое в очереди видео больше не остаётся «в очереди»; задание
  воркера, который не подаёт признаков жизни дольше двух минут, отменяется сразу; панель говорит,
  что именно произошло.
- **Уборка временных файлов** прерванных заданий (сборка монтажа, промежуточные файлы правки и
  размытия) старше 12 часов.
- **События между процессами** (прогресс, чат, уведомления) больше не пропадают после перезапуска
  PostgreSQL или «полуоткрытого» соединения: слушатель переподключается и проверяет связь раз в минуту.
- Кадры предпросмотра в редакторах — не больше трёх ffmpeg одновременно (`PREVIEW_CONCURRENCY`) и с
  пределом времени: быстрая перемотка по таймлайну не поднимает десятки процессов.

### Настройки, которые теперь работают

Шесть ключей показывались администратору, но ничем не читались:

- `webinars.reminders` — расписание напоминаний о вебинаре (минуты до начала, до шести значений,
  от 5 минут до недели);
- `webinars.followup` — выключатель письма-послесловия;
- `webinar.attendance_min_percent` — с какой доли эфира участие засчитывается (письмо, отчёт, список
  участников); поле переехало в раздел «Трансляции» рядом с остальными настройками вебинаров;
- `party.everyone_controls` — кто управляет совместным просмотром по умолчанию;
- `premiere.chat_default` — чат премьеры по умолчанию;
- `lifecycle.freshness_months` — «актуально до» для новых видео (загрузка, импорт, клипы, монтаж,
  записи эфиров, автоимпорт).

Новый ключ: `feeds.token_days` — срок жизни личного токена лент.

### Вебинары

- **Материалы** раздаются отдельным адресом с проверкой: «до вебинара» — всем, кто видит страницу,
  остальные — только подтверждённым участникам и организаторам; всегда вложением и с запретом
  угадывания типа. Принимаются только документы, презентации, таблицы, архивы и картинки — тот же
  список, что у материалов к видео. В письме-послесловии у внешнего участника — ссылки с его личным
  токеном. Раньше материалы через `/media/` не открывались вовсе.
- **Обложки вебинаров и витрин** раздаются (раньше — отказ), причём только тем, кому видна страница.
- **Письмо-послесловие** получает каждый участник ровно один раз: отметка ставится по адресату, и
  сбой посреди рассылки больше не приводит к повторным письмам.
- **Присутствие** копится только во время эфира и не быстрее реального времени: частые запросы и
  несколько открытых вкладок больше не накручивают время, от которого зависит сертификат. Сотрудники
  попадают в кривую присутствия (раньше — только гости), гость по ссылке из письма отмечается и на
  странице эфира.
- **Соведущие**: назначает организатор (или администратор), соведущий получает уведомление и может
  отказаться от роли. В студии — блок «Соведущие» с поиском сотрудников.
- **Автовебинар** можно собрать только из своего видео.
- Запись на вебинар ограничивается по сотруднику, а не по адресу офиса.

### Производительность

- **Главная и «Тренды»**: двухнедельная статистика агрегируется один раз, а не подзапросом для
  каждого видео при каждом заходе.
- **«Похожие видео»** считаются по кандидатам, найденным по индексам (категория, автор, теги, слова
  названия, популярное и новое), а не по всей библиотеке.
- **Поиск «по идентификатору или короткому адресу»** идёт по индексу. Раньше приведение столбца к
  тексту выключало индекс, и каждое открытие видео, эфира или плейлиста (и каждый сигнал прогресса
  просмотра) проходило таблицу целиком.
- **Опросы эфира и вебинара**: два запроса на все опросы вместо двух на каждый (было до 101 запроса
  на одно открытие страницы).
- **Суточная уборка** удаляет устаревшие строки пачками по 10 000.

### Безопасность

- **Исходящие запросы** (вебхуки, ИИ, ASR, база знаний, LRS, SSO, Telegram) проверяют адрес на каждом
  перенаправлении; администратору показывается короткая подсказка из ответа, а не тело целиком.
- **Плейлист** больше не раскрывает закрытые видео: такая позиция показывается как «Видео недоступно»
  без названия, автора и описания.
- **Код TOTP одноразовый** — подсмотренный код нельзя ввести повторно в пределах окна.
- **Лимит открытий защищённой ссылки** неделим: одновременные открытия последнего «слота» не проходят оба.
- **Токены в адресах** (`?ft=`, `?t=`, `?token=`) маскируются в журнале доступа nginx.
- `?t=` принимается как токен участника только на адресах вебинаров и эфиров.
- Поиск экранирует `%` и `_` — запрос из одного символа больше не совпадает со всем подряд.
- Цвет акцента портала и витрин — только `#RRGGBB`; путь миниатюры нормализуется.
- Приём метрик плеера и отметки присутствия — с собственными пределами частоты.
- **Квота на канал** учитывает файлы проектов графического редактора и незавершённые загрузки;
  проверка и запись идут под блокировкой, параллельные загрузки квоту не обходят. Файл проекта больше
  предела больше не сохраняется обрезанным.
- Скачиваемые через nginx файлы получают `nosniff` и песочницу; имена с кириллицей отдаются
  правильно (раньше — ошибка 500 на материале «Памятка.pdf»).
- Адрес экрана-телевизора в панели — проверенный адрес, а не присланный клиентом заголовок.

### Интерфейс

- **Ошибка вместо «Пока ничего нет»**: при сбое сети списки показывают, что случилось, и кнопку
  «Повторить» — тренды, новое, история, понравившиеся, подписки, категории, теги, поиск, уведомления,
  журналы и очереди панели, комментарии, курсы и вебинары студии.
- **Плеер при обрыве сети** пишет «Связь прервалась — восстанавливаем…» и повторяет с растущей паузой
  (запись — шесть попыток, эфир — без ограничения), затем показывает сообщение и «Повторить»; когда
  сеть возвращается, продолжает сам. Раньше плеер молча замирал, а на эфире каждая ошибка заводила
  новый таймер.
- **Подписи у ~170 кнопок-иконок** для экранного диктора; выпадающие меню работают с клавиатуры
  (стрелки, Home/End, Esc возвращает фокус); подсказки поиска размечены как список вариантов.
- **Скачивание для офлайна** пишется в кэш потоком, а не собирается в памяти вкладки; портал заранее
  проверяет свободное место; скачанное видео можно перематывать и в Safari.
- **Таблицы и длинные строки на телефоне** прокручиваются, а не обрезаются («Скачанные», «Экраны»,
  «Система», адреса лент, ключи).
- **Сервис-воркер** получает новую версию кэша с каждой сборкой — после обновления портала
  браузеры больше не держат старую оболочку.
- Совместный просмотр, «Короткие» и экраны не оставляют таймеров и перехвата клавиш, если уйти со
  страницы во время загрузки; WebSocket переподключается, если сервер молчит дольше 75 секунд.
- В панели администратора без обязательного второго фактора — одно предупреждение вместо разделов
  с ошибками.
- Отступы, которые в разметке были, а в стилях — нет (`mt-12`, `mb-4`, `gap-12` и двухколоночные
  поля): блоки настроек и форм больше не слипаются, а вид страницы не зависит от того, какие
  разделы открывали до неё.

### Установка и эксплуатация

- Установщик проверяет занятые порты и длину пароля администратора **до** начала установки;
  временные файлы — с непредсказуемыми именами; повторный запуск больше не меняет пароль

- Перенаправление на HTTPS идёт на имя портала с учётом нестандартного порта, а не на заголовок
  запроса (`PUBLIC_HTTPS_PORT` в Docker).
- Docker: контейнерам приложения монтируются только нужные каталоги (`media`, `uploads`, `live`,
  `import`) — база, резервные копии и сертификаты в контейнер не попадают.
- `update.sh` включает MediaMTX в автозапуск и шире проверяет целостность архива.
- `corpvideo cli` на нативной установке передаёт аргументы как есть: команда
  `settings set site.name "Мой портал"` раньше распадалась на два слова, а пароль с пробелом или

### Проверка кода: что нашли и починили

Проведён сквозной разбор сервера, интерфейса, безопасности и установки. Существенное:

**Потеря данных и невыполнимые обещания**
- **Удалённое видео теперь действительно можно восстановить.** Удаление стирало файлы сразу, и
  «Восстановить» в панели всегда отвечало «Файлы видео были удалены» — то есть корзина
  (`retention.trash_days`) не работала никогда. Теперь файлы удаляет только окончательная уборка
  по истечении срока.
- **Живые субтитры эфира больше не теряются**: расшифровка записывалась в несуществующие колонки,
  ошибка молча гасилась, и у записи эфира субтитров не появлялось.
- **Видео не зависает «в обработке»**: при отмене или сбое задания сущность теперь переводится в
  понятное состояние. Появился **предел времени на задание** — зависший ffmpeg или сетевой запрос
  больше не держит слот воркера вечно.
- **Двойной клик на «Обработать заново»** больше не запускает два ffmpeg на один каталог.

**Безопасность**
- **Чужая ссылка на вебинар**: повторная анонимная регистрация по чужой почте возвращала
  персональную ссылку участника. Теперь ссылка уходит только письмом на этот адрес.
- **SVG-вложение** больше не может выполнить скрипт на домене портала: файл не открывается в окне
  браузера, а `/media/` отдаётся с запретом угадывания типа и песочницей.
- **Импорт по ссылке** проверяет адрес на каждом перенаправлении — раньше ответ «302 на внутренний
  адрес» обходил проверку. Ретрансляция теперь разрешает имя площадки, а не смотрит на вид строки.
- **Вход через SSO** связывает внешнюю учётку с местной по почте только если провайдер подтвердил адрес.
- **Подбор второго фактора** считается наравне с подбором пароля и блокируется.
- **Приглашения** видит и создаёт только администратор: модератор мог активировать чужое приглашение
  с ролью администратора.
- **Хук MediaMTX без секрета** отвечает отказом, а не пускает всех.
- **Выгрузка CSV** обезвреживает значения, начинающиеся с `=`, `+`, `-`, `@` — Excel больше не
  выполнит формулу из названия видео или ответа анкеты.
- **Миниатюра закрытого эфира** отдаётся только тем, кому виден сам эфир.

**Точность и устойчивость**
- Места на вебинаре, лист ожидания и приём части файла больше не портятся при одновременных
  действиях: проверка и запись стали неделимыми.
- **Присутствие на вебинаре** считается по людям, а не по сигналам плеера (раньше минута с одним
  участником показывала двоих).
- «Повторить все неудачные задания» больше не перезапускает монтаж и сборку клипов — их повтор
  применял правки второй раз.
- Правило хранения с действием «предупредить» больше не шлёт письмо каждую ночь.
- Настройки сохраняются целиком или никак; варианты качества пишутся одной транзакцией.
- Суточная уборка получила индексы — на больших таблицах она перестала быть долгим проходом.

**Интерфейс**
- **Вернулись рамки и разделители**: переменные `--border` и `--muted` были объявлены только в режиме
  повышенной контрастности, хотя использовались в обычных стилях двух десятков мест.
- **Вкладки поиска** («Каналы», «Плейлисты», «Трансляции») показывали «ничего не найдено» при
  непустом ответе.
- **Заблокированное хранилище браузера** (корпоративная политика, приватный режим) больше не рвёт
  запуск приложения — раньше вместе с ним молча отключались живые уведомления.
- Списки не «залипают» на устаревшем ответе при быстром переключении фильтров, а переход по
  страницам больше не отправляет два одинаковых запроса.
- **Диалоги** удерживают фокус, объявляют заголовок и возвращают фокус на место; всплывающие
  сообщения читаются экранным диктором; на телефоне кнопки диалога больше не уезжают под панель браузера.
- **При выходе из системы** чистятся скачанные видео и запомненная конфигурация — на общем

- Страницы студии и разделов проверяют права до открытия, а не после выбора файла.

**Установка и эксплуатация**
- `update.sh` **проверяет архив** перед тем, как заливать его поверх установки: при битом архиве

- `backup.sh` проверяет **свободное место** перед архивом медиа, кладёт в копию **сертификаты и
  незаимпортированные записи эфиров**, проверяет читаемость дампа и пишет **контрольные суммы**.
- Установщик заводит **ротацию журналов** и **ежедневную резервную копию по расписанию**.
- Новая команда **`corpvideo doctor`** — одна сводка для разбора любой жалобы: службы, порты,
  проверка конфигурации nginx, срок сертификата, диск, последняя копия, доступность портала.
- Нативная установка получила **сжатие** и `server_tokens off` (раньше это было только в docker).
- Закрыта **та же ловушка nginx**, что и в 1.10.5, на адресе `/whip` (эфир из браузера и OBS).
- Секрет хуков MediaMTX и журнал установки больше не читаются посторонними на сервере.

## 1.10.5 — найдена причина: nginx перенаправлял создание загрузки (17 сентября 2026)

**Это была ошибка в поставляемой конфигурации nginx, а не в сети заказчика.** Обновление обычное:
`sudo ./update.sh` (или `corpvideo update`) — оно и пересобирает веб-интерфейс, и заново создаёт
конфигурацию nginx. Миграций нет.

### Что происходило

В конфигурации был блок `location /api/uploads/` с `proxy_pass` — для крупных частей файла. По
документации nginx, префиксный `location`, оканчивающийся на косую черту, вместе с `proxy_pass`
заставляет сервер отвечать **301** на запрос ровно этого адреса **без** косой черты. А
веб-интерфейс создавал загрузку запросом `POST /api/uploads` — без косой черты.

Дальше срабатывало правило браузеров: на 301 запрос **POST превращается в GET и теряет тело**.
Вместо создания загрузки на сервер уходил `GET /api/uploads/` — то есть запрос состояния загрузки
с пустым идентификатором. Отсюда и все сообщения, которые видел администратор:

| Версия | Что показывалось | Почему |
|---|---|---|
| до 1.10.1 | «Некорректный идентификатор или значение в запросе» | пустой идентификатор доходил до PostgreSQL и тот отвечал ошибкой типа `uuid` |
| 1.10.1–1.10.2 | «Загрузка не найдена» | добавленная проверка идентификатора отсекала пустое значение раньше базы |
| 1.10.3–1.10.4 | «Ошибка (код 404): Загрузка не найдена» | то же самое, но уже с кодом ответа |

Всё это время загрузка **не начиналась вовсе**: индикатор оставался на нуле, ни один байт не уходил.
В песочнице ошибка не воспроизводилась, потому что там nginx перед порталом нет — файл грузился
напрямую в API. Это и было слепым пятном проверок.

### Исправлено

- **Конфигурация nginx**: добавлен точный блок `location = /api/uploads` (способ, прямо описанный в
  документации nginx). Перенаправления больше нет.
- **Веб-интерфейс** обращается к каноническому адресу `/api/uploads/` — с косой чертой. Благодаря
  этому загрузка чинится сразу после обновления, даже если конфигурацию nginx правили вручную и она
  не перегенерировалась.
- **Перенаправление любого запроса к API теперь считается ошибкой**: браузер на нём теряет тело
  запроса, поэтому портал прямо пишет, какой адрес и куда был перенаправлен, вместо молчаливой порчи.
- **Проверка загрузки** получила шаг **«Адрес без косой черты»**: она отдельно проверяет именно этот
  случай и называет нужную правку в nginx.
- Проверки: загрузка файла **через настоящий nginx** теперь входит в регрессию (раньше проверялась
  только напрямую в API), плюс тест шаблона nginx — у каждого проксируемого адреса API с косой чертой
  обязан быть парный точный `location`.

### Мелочи

- Сводка качества воспроизведения в тестах перестала зависеть от того, что лежит в пяти последних
  загрузках студии.

## 1.10.4 — проверка загрузки теперь показывает, где пропадает загрузка (17 сентября 2026)

Третий шаг разбора той же жалобы. После 1.10.3 сообщение стало точным — «Ошибка (код 404): Загрузка не
найдена», — и оно означает совершенно определённое: идентификатор загрузка получает нормальный, а
следующий запрос по этому идентификатору её уже не находит. То есть запись создаётся и пропадает между
двумя запросами. Обновление обычное, миграций нет.

### Кнопка «Проверить загрузку» стала подробнее

- **Связь с порталом** — портал опрашивается трижды, и в ответе теперь есть метка экземпляра. Если на
  один адрес отвечают **разные экземпляры** (осталась служба от прежней установки, балансировщик на два
  сервера, два контейнера), проверка так и пишет: загрузка по частям при этом работать не может, потому
  что часть уходит не туда, где загрузка создана.
- **Чтение созданной загрузки** — новый шаг: только что созданная запись читается обратно три раза.
  «3 из 3» — запись на месте; «ни разу» или «через раз» — запросы попадают в разные базы. Именно этот
  шаг отделяет пропажу записи от проблем с отправкой самой части.
- Отправка части теперь отдельно объясняет **401** (запрос ушёл без входа — режут cookie),
  **404** (часть уходит не на тот сервер) и **413** (не пропустил веб-сервер).
- В шаге создания видно хвост идентификатора — его удобно сверить с журналом сервера.

### Загрузка чинит себя сама

- Если части отвечают «загрузка не найдена» **на первой же части**, портал заводит загрузку заново и
  повторяет отправку — один раз, чтобы не ходить по кругу. Разовая пропажа (перезапуск сервера ровно в
  этот момент, устаревшая запись) больше не требует ничего от человека.
- Если и после этого не нашлась, в карточке пишется прямая подсказка: загрузка пропадает сразу после
  создания, так бывает при нескольких экземплярах портала на одном адресе.

### Мелочи

- `GET /api/health` возвращает поле `instance` — постоянную метку процесса. Полезно и для мониторинга:
  по смене метки видно перезапуск, по разным меткам подряд — что за адресом не один сервер.

## 1.10.3 — портал больше не прячет чужие ответы при загрузке (17 сентября 2026)

Продолжение разбора жалобы «Ошибка: Некорректный идентификатор или значение в запросе» при добавлении
видео. Обновление обычное: `sudo ./update.sh` (или `corpvideo update`), миграций нет.

### Что было на самом деле

Интерфейс молча принимал **любой** успешный ответ на создание загрузки, даже если это была не наша
JSON-строка, а HTML-страница от прокси, VPN или антивируса. Идентификатор загрузки получался пустым,
следующий запрос уходил на `/api/uploads/undefined`, и человек видел либо «Некорректный идентификатор
или значение в запросе» (до 1.10.1), либо «Загрузка не найдена» (1.10.1–1.10.2) — ни то, ни другое
не указывало на настоящую причину.

### Исправлено

- **Ответ не в формате портала больше не проглатывается**: и при загрузке, и в любом другом запросе
  портал сообщает код ответа, тип содержимого и начало текста — сразу видно, что ответ подменили
  по дороге (страница прокси, вход в корпоративную сеть, антивирус).
- **Пустой идентификатор загрузки отсекается сразу**, до отправки файла, с понятным сообщением.
- **«Продолжить» после пропавшей загрузки** (сервер перезапустили, загрузка устарела или была отменена)
  начинает заново, а не упирается навсегда в «Загрузка не найдена».
- **Часть файла принята — значит ответ с числом принятых байт**: иначе докачка останавливается
  с объяснением, а не идёт вразнос.
- В карточке файла рядом с ошибкой виден **код ответа** — этого достаточно для обращения к администратору.
- Промахи по идентификатору загрузки **пишутся в журнал API** (сам идентификатор, маршрут, пользователь):
  `corpvideo logs api` показывает, например, обращение к `/api/uploads/undefined`.

### Кнопка «Проверить загрузку»

В **Студия → Загрузка** появилась проверка, проходящая тот же путь, что и настоящий файл: связь с
порталом → создание загрузки → отправка части нужного размера → уборка. Каждый шаг отмечается отдельно,
и в конце портал называет сломанный шаг. Отдельно распознаётся ответ 413 — часть не пропустил
веб-сервер (нужно поднять `client_max_body_size` для `/api/uploads/` в nginx).

## 1.10.1 — предел загрузки 2 ТБ и понятные ошибки при добавлении видео (17 сентября 2026)

Обновление обычное: `sudo ./update.sh` (или `corpvideo update`). Миграция `012_upload_limit.sql`
поднимает сохранённый предел до 2 ТБ только там, где он остался прежним по умолчанию (8192 МБ) —
осознанно выставленный администратором лимит не трогается.

### Загрузка больших файлов

- **Предел размера файла — 2 ТБ** вместо 8 ГБ (`upload.max_size_mb` = 2097152). В настройках рядом
  с полем показывается человеческий размер.
- **Размер части подстраивается под файл**: до 10 ГБ — 8 МБ, до 100 ГБ — 16 МБ, до 500 ГБ — 32 МБ,
  дальше — 64 МБ. На терабайтном файле это сотни тысяч запросов превращает в десятки тысяч.
- Подняты внутренние пределы: приём части до 80 МБ, простая загрузка одним запросом — до 2 ТБ.

### Ошибка «Некорректный идентификатор или значение в запросе»

- **Причина устранена**: нечисловое значение категории (или размера файла) уходило в базу как `NaN`,
  и PostgreSQL отвечал ошибкой типа. Теперь такие значения отбрасываются: категория считается
  незаданной, а про размер приходит понятное сообщение.
- Мусорный идентификатор загрузки (`/api/uploads/undefined`) больше не превращается в ошибку базы —
  отвечает «Загрузка не найдена».
- Такие ответы теперь **пишутся в журнал API** с кодом PostgreSQL, таблицей, колонкой и маршрутом,
  а в сообщении видно само значение и ожидаемый тип — разобрать похожую жалобу можно по `corpvideo logs api`.

## 1.3.1 — аудит кода (16 сентября 2026)

Функции не менялись: выпуск целиком состоит из исправлений, найденных при сплошной проверке кода.
Обновление обычное: `sudo ./update.sh` (или `corpvideo update`). Миграций базы нет.

### Важно для администраторов

- **API-токены больше не дают доступ к разделу администрирования.** Токены всегда создавались с областями
  `upload` и `read`, но проверка прав смотрела только на роль владельца, поэтому токен администратора открывал
  весь `/api/admin/*`. Теперь такие вызовы возвращают 403. Если у вас есть сценарии автоматизации,
  обращавшиеся к `/api/admin/...` по токену, их нужно перевести на вход по паролю (cookie-сессия).
- **Секрет вебхука больше не приходит в списке вебхуков.** В таблице показывается только начало секрета,
  полный выдаётся по кнопке «Скопировать секрет» (обращение записывается в журнал аудита).
- **Замена файла видео сбрасывает расшифровку речи и распознанный текст с экрана** — они относились
  к прежней версии файла. Автосубтитры создаются заново, поиск больше не показывает старые тайм-коды.

### Безопасность

- Поиск: фильтр «HD» отменял ограничение видимости — гость получал внутренние и приватные видео
  (условие `OR` без скобок). Условие видимости теперь всегда заключено в скобки.
- Поиск: подсветка совпадений в расшифровке и тексте с экрана возвращалась как сырой HTML — добавлено
  экранирование с сохранением только `<b>`.
- Вход через SSO (OIDC): ответ провайдера теперь принимается только в том браузере, где вход начинался
  (state привязан к cookie), `iss` обязателен, `nonce` проверяется.
- Прокси HLS трансляций: имя файла проверяется по белому списку символов, ключ потока экранируется.
- Сброс ключа трансляции разрешён только владельцу и администратору.
- Выгрузка одного документа в RAG проверяет видимость и статус модерации видео; токен сравнивается
  за постоянное время.
- Счётчик просмотров: гостевой идентификатор берётся из подписанной cookie — подделкой заголовка
  больше нельзя накрутить просмотры.
- Ссылка на сброс пароля выдаётся только администратору.
- Ограничение частоты запросов обходилось строкой запроса вида `?x=/hls/` — список исключений
  сверяется только с путём.
- Комментарий модератора виден только автору видео, модераторам и администраторам.
- События приватных трансляций по WebSocket уходят только владельцу и администраторам.
- Назначение плейлиста больше не раскрывает чужие приватные видео.
- Клип нельзя создать по временной ссылке-приглашению и из видео с запретом скачивания.
- SCORM-страница принимает сообщения о прогрессе только от собственного плеера (проверка окна и origin),
  встраиваемый плеер — только от встраивающей страницы.
- `LDAP: проверять сертификат` включено по умолчанию; `TRUST_PROXY` понимает значения из окружения.
- Резервные копии создаются с правами 700/600 (`umask 077`), неполная копия удаляется, дамп перед
  восстановлением проверяется, а после восстановления проверяется, что база не пуста.
- nginx в Docker монтирует только каталог медиафайлов, а не весь каталог данных.
- Отдача файлов из `/assets/` не позволяет выйти за пределы каталога.

### Надёжность

- Монтаж (обрезка, вырезание, удаление пауз) нельзя запустить дважды для одного видео: проверка и
  постановка задания выполняются под межпроцессной блокировкой PostgreSQL.
- Остановка воркера больше не «возвращает» попытку: одноразовые задания (монтаж, клип) не выполняются
  повторно после перезапуска; задания живого соседнего воркера не трогаются.
- Обслуживание выполняется ровно одним воркером (advisory lock), ручной запуск не теряется.
- Главы пересчитываются при любом монтаже, а не только при обрезке начала.
- Долгие сетевые задания (ИИ, RAG, перевод субтитров) вынесены в отдельную полосу — письма и вебхуки
  больше не ждут их завершения.
- OCR: задание не помечается выполненным, если не распознан ни один кадр.
- xAPI: ответ LRS 409 (повторная отправка) считается успехом.
- RSS/Atom: управляющие символы в описаниях больше не ломают ленту, размер вложения берётся из файла,
  устранено повторное объявление `xmlns:atom`, из-за которого видео-ленты были невалидным XML.
- ZIP-упаковщик (SCORM) работает на Node < 20.15 (запасной расчёт CRC32).
- Список назначений: сводка и адресаты собираются пакетно — вместо ~60 запросов на страницу 4.
- Пересобранный веб-интерфейс подхватывается без перезапуска API.

### Интерфейс

- Копирование в буфер обмена работает и на порталах без HTTPS; при неудаче показывается честное сообщение.
- Настройки администратора: при ошибке загрузки — сообщение и кнопка «Повторить» вместо вечного индикатора.
- Панель вебхуков: обработка ошибок, отмена отложенных обновлений, защита от обращения к удалённому вебхуку.
- Плеер: слушатель `beforeunload` снимается при уходе со страницы; переключение режима «только звук»
  не запускает поставленное на паузу видео.
- Очередь: открытое видео убирается из очереди и не предлагается как следующее.
- Студия: отметка «есть несохранённые изменения» больше не появляется сразу после загрузки; при уходе
  со страницы с несохранёнными правками портал спрашивает подтверждение.
- Просмотр: быстрый переход между видео не подставляет данные предыдущего.
- Конечная заставка: ссылка проверяется в интерфейсе так же, как на сервере.

### Установка и обновление

- `.gitignore` исключал каталог `deploy/mediamtx/` целиком — из-за этого при установке из git-репозитория
  не находился шаблон конфигурации MediaMTX. Исправлено.
- Перед установкой проверяется комплектность дистрибутива со списком недостающих файлов.
- `npm ci` повторяется до трёх раз с увеличенными таймаутами, при неудаче пробуется `npm install`,
  а при отсутствии доступа к registry используется готовый `web/dist` из дистрибутива.
- При сбое сборки выводятся последние строки журнала; отдельно распознаётся нехватка памяти.
- Обновление использует ту же логику сборки, что и установка; версия в `install.conf` фиксируется
  только после успешного завершения.
